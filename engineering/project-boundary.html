Problem framing

Make unsafe motion structurally difficult.

Autonomy systems become difficult to trust when mission logic, sensor health, safety state, and actuator authority blur together. Project Boundary separates those concerns so the system can answer who requested motion, who authorized it, what condition changed, and why the final command was allowed.

Mission software is allowed to request movement. It is not allowed to authorize movement. Every actuator command must pass through the safety supervisor and motion-arbitration boundary before the hardware gateway can execute it.

Fault injection follows the same rule. Faults alter inputs, timing, freshness, or confidence and force the normal safety path to react. They do not reach into the state machine and set a convenient result directly.

Architectural thesis

Mission systems may request motion. Only the safety system may authorize motion.

Runtime architecture

Separate intent from authority.

The critical path is deliberately small. Mission intent, sensor confidence, safety enforcement, motion arbitration, and actuator execution are isolated so each boundary can be tested and audited.

In the ROS 2 integration, mission and operator code publish requested motion, the safety bridge is the only producer of authorized motion, and the Gazebo bridge forwards only the authorized command path.

Safety authority boundary

The hardware gateway subscribes to the authorized command channel, not the requested command channel. SAFE_STOP and E_STOP_LATCHED actively publish zero motion. Recovery is gated rather than treated as an automatic return to normal operation.

Verification evidence

Test the authority model under failure.

The deterministic verification engine exercises nominal operation, sensor degradation, command loss, bridge disconnects, E-stop behavior, mission recovery, keepout constraints, restricted operation, and fault escalation. Each scenario records the expected state, events, command-path audit, transition audit, and replay-integrity result.

Fault behavior is exercised through normal pathways

Stale LiDAR, sensor disagreement, command timeout, bridge disconnect, wheel slip, and related faults alter conditions the supervisor observes. The verifier checks the resulting transition and command behavior.

Safe-stop zero motion is explicitly checked

Scenarios that terminate in SAFE_STOP or E_STOP_LATCHED include a zero-motion assertion rather than assuming the state label alone proves actuator behavior.

Replay integrity is part of the result

Verification includes replay-integrity and safety-transition audits so a passing outcome retains the evidence needed to reconstruct why the system reached that outcome.

ROS runtime maturity is reported separately

Deterministic-engine scenario success is not presented as proof that every ROS 2 / Gazebo runtime path has executed live. Static validation and host-dependent execution remain distinct claims.

Engineering decisions

Optimize for inspectability, not novelty.

The strongest design choices are the constraints that make later verification possible.

01

One subsystem owns motion authorization

The safety supervisor owns the final authorization boundary. Mission software can request movement but cannot bypass arbitration or write directly to actuator interfaces.

02

Determinism stays in the critical path

Critical safety behavior favors bounded state transitions, explicit limits, reproducible scenarios, and reason-coded decisions over probabilistic autonomy.

03

Fault injection changes inputs, not outcomes

A fault may disturb sensor data, timing, freshness, or a watchdog. It may not set the safety state directly, preserving causal fidelity in the test path.

04

Replay is an operational requirement

State transitions, actuator commands, confidence changes, mission events, and safety interventions are recorded so incidents can be reconstructed rather than explained from memory.

05

Simulation and hardware share contracts

The deterministic core and the ROS 2 / Gazebo path preserve the same requested-versus-authorized motion model so simulation does not become a separate architectural universe.

06

Report incomplete evidence honestly

Runtime reports distinguish passed, failed, partial, skipped, and not-executed states. Host-dependent ROS execution is not silently promoted into a stronger claim than the evidence supports.

Boundaries and limitations

Safety-oriented does not mean safety-certified.

Project Boundary is an engineering-learning and portfolio system. Its value comes from the architecture and verification discipline it demonstrates, not from implying compliance or real-world certification.

No functional-safety certification claim

The safety model explicitly does not claim ISO 13849, ISO 26262, IEC 61508, or other functional-safety certification.

Live ROS execution is environment-dependent

The ROS 2 Jazzy / Gazebo Harmonic path is implemented and statically validated, but full end-to-end runtime verification requires a compatible Jazzy host.

Simulation is not hardware validation

The platform is simulation-first. Shared contracts reduce architectural drift, but physical actuators, hardware timing, transport failures, and real sensor behavior remain a separate validation problem.

Autonomy scope is deliberately bounded

Camera-first perception, uncontrolled AI autonomy, reinforcement-learning control, swarms, and other complexity are deferred so safety authority, replay, and fault behavior remain inspectable.

Maturity path

Preserve the authority model as realism increases.

The next maturity steps are not about adding autonomous behavior for its own sake. They are about proving the same safety and replay contracts under more realistic middleware, simulation, timing, and hardware conditions.

Current evidence

  • Dependency-light deterministic Python safety and mission core.
  • Generated scenario verification and replay evidence.
  • ROS 2 Jazzy / Gazebo workspace with static architectural validation.
  • Reviewer-oriented traceability and evidence exports.

Higher maturity

  • Run repeatable end-to-end Jazzy / Gazebo qualification in a supported host environment.
  • Capture real rosbag / MCAP runtime evidence and source-change series.
  • Exercise the same authorization contracts against physical hardware and real sensor timing.
  • Keep probabilistic features advisory unless a governed safety argument justifies otherwise.

Engineering work

Inspect the safety boundary, not just the rover demo.
