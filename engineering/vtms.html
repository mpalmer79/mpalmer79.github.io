Problem framing

Build the engineering model before building the product around it.

VTMS started with a system-modeling question rather than a UI requirement: can a compact, deterministic model represent the transient thermal behavior of an internal-combustion vehicle cooling system well enough to support engineering analysis, and can that claim be tested without confusing numerical correctness with physical accuracy?

The engineering challenge

A thermal-management simulator has to connect heat generation, engine thermal storage, coolant energy storage, engine-to-coolant transfer, radiator rejection, thermostat behavior, pump flow, fan airflow, ram airflow, ambient conditions, and operating inputs through a model that remains deterministic and testable.

The harder problem is credibility. A simulation that runs is not necessarily a model that predicts reality. VTMS therefore treats model specification, numerical verification, calibration, holdout validation, and product presentation as different engineering concerns.

Core question

Can the system preserve a clean evidence trail from frozen equations to implementation, independent physical comparison, and an honest acceptance decision, even when the result fails?

Model boundary

A two-state transient thermal model.

VTMS-V1 integrates effective engine-structure temperature and bulk engine-side coolant temperature. Radiator outlet temperature is algebraic rather than a third integrated state.

Frozen governing structure

The V1 model deliberately uses a compact lumped-parameter representation. It is intended to make assumptions visible, preserve deterministic behavior, and support controlled verification and validation before adding more physical states. 

C_e dT_e/dt = Q_engine - Q_ec - Q_ea
C_c dT_c/dt = Q_ec - Q_rad

Q_ec = UA_ec (T_e - T_c)
Q_ea = UA_ea (T_e - T_a)

System architecture

Keep the physics authoritative and the product boundary clean.

The browser never calculates governing thermal physics. The web interface submits a scenario through FastAPI, the authoritative Python simulation runner executes the model, and the API returns the simulation record. Validation tooling remains separate from both transport and UI.

Verification

Prove the implementation before judging the model.

Numerical verification asks whether the code solves the frozen VTMS-V1 equations consistently. It does not establish vehicle-specific physical accuracy.

Verification is not validation

Passing conservation, convergence, component invariants, regression behavior, API translation, provenance, bounded calibration, identifiability, and holdout-protection checks establishes implementation discipline. It does not prove that the model reproduces a real vehicle within the project acceptance criteria.

Controlled physical validation

The model failed, and the failure was preserved.

VTMS assigns every external run exactly one evidence role before formal analysis: plausibility, calibration, holdout, or challenge. Only calibration permits parameter fitting. Holdouts prohibit fitting and cannot be recycled into calibration after their residuals are observed.

Engineering interpretation

Revise the model form, not the evidence

The two independent holdouts underpredicted final coolant temperature by approximately 8.5 °C. With calibrated parameters pressing against frozen bounds, the next step is a governed model revision rather than more V1 parameter tuning.

Engineering decisions

The decisions matter as much as the solver.

The strongest VTMS evidence is not that an ODE solver runs. It is the set of controls that keep implementation, calibration, validation, and product presentation from contaminating one another.

01

Freeze V1 before physical fitting

The equation set, component topology, numerics, scenarios, and calibration universe were constrained before controlled residual inspection so validation could test a defined model.

02

Keep physics out of the browser

Next.js presents the engineering product. FastAPI validates requests and invokes the authoritative Python SimulationRunner. Governing thermal calculations stay in one execution layer.

03

Separate verification from validation

Numerical correctness is necessary but not sufficient. The project reports passing verification and failed physical validation as two simultaneous facts rather than collapsing them into one status.

04

Assign evidence roles before analysis

Plausibility, calibration, holdout, and challenge roles determine what an external dataset may be used to claim. A holdout cannot authorize fitting after its model residual becomes known.

05

Use identifiability to constrain fitting

Synthetic pre-fit diagnostics showed radiator UA was weakly excited by warm-up profiles, so a simultaneous four-parameter CAL-01 fit was prohibited even though an optimizer could move it.

06

Preserve the failed holdout

Bounds were not expanded, roles were not reassigned, and the failed holdouts were not reused for V1 fitting. The evidence now supports a new model-form revision instead of post-hoc tuning.

Boundaries and limitations

State what the model does not know.

Staff-level engineering credibility depends on visible boundaries. VTMS-V1 intentionally excludes several physical effects and does not claim vehicle-specific digital-twin maturity.

Not an OEM vehicle model

Effective lumped parameters are engineering abstractions. Calibrated values are not uniquely identified Ford component properties and should not be interpreted as such.

Not a synchronized digital twin

VTMS-V1 has no live vehicle synchronization, vehicle-specific state estimation, governed online calibration, or continuously synchronized telemetry loop.

Thermal scope is intentionally limited

V1 excludes coolant pressure and boiling, two-phase flow, detailed jacket hydraulics, oil as a separate state, HVAC and heater-core loads, transmission cooling, local hot spots, and underhood CFD.

High-temperature fault cases are qualitative

Conditions above the liquid-only caution boundary are useful for system-behavior exploration but are not predictions of boiling, mechanical damage, or vehicle safety outcomes.

Next governed revision

What V2 should learn from V1.

Because the original Argonne holdouts have now been observed, they may inform V2 model development but cannot be relabeled as new blind validation evidence. A revised model will require a new preregistered calibration and independent-validation program.

Model-form investigation

  • Use preserved residual patterns to identify missing thermal states or topology limitations.
  • Justify any added state or control behavior physically before implementation.
  • Keep the V1 failure record intact as the baseline engineering evidence.

Higher maturity path

  • Add stronger uncertainty and sensitivity treatment.
  • Introduce vehicle-specific OBD-II/CAN replay only under explicit evidence controls.
  • Reserve synchronized telemetry and state estimation for a future true digital-twin maturity stage.
